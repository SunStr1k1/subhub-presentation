SubHub

Веб-приложение для управления подписками: все регулярные платежи — в одном месте, с честным пересчётом в месяц и напоминаниями о продлениях.

Проблема

Подписки утекают незаметно

💸

Невидимые траты

Стриминги, SaaS, AI-сервисы, хранилища. Человек не видит общую сумму — каждый платёж приходит отдельно.

⏰

Внезапные списания

Пробный период кончился, автопродление сработало. Почта завалена — календарь не спасает.

🧮

Разные валюты и периоды

Три сервиса по €5 в неделю, два по $12 в год… существующие трекеры не умеют сводить это в «сколько я плачу в месяц».

Опросы рынка: сервисы-трекеры либо перегружены корпоративным дизайном, либо навязывают одну валюту.

Решение

SubHub — один честный экран ваших расходов

  • Единая картина — каждый платёж пересчитывается в настоящую месячную сумму (неделя / квартал / год → месяц).
  • Каталог Explore — выбираешь сервис из базы, подписка создаётся с предзаполненными ценой и периодом, но свои значения всегда подтверждаешь сам.
  • Аналитика — максимальная трата, распределение по категориям, график по месяцам, список ближайших продлений.
  • Календарь платежей — месяц целиком, с днями, когда спишутся деньги.
  • Напоминания — уведомления о продлении до списания (приложение + планировщик писем).
  • Международность с первого дня — несколько валют (ISO 4217), локализованное форматирование чисел и дат.
Технологии

Почему такой стек

▲

Next.js 16 (App Router) + React 19

Server Components и Server Actions: данные рендерятся на сервере, клиент получает лёгкий UI. Turbopack собирает проект.

🛡️

TypeScript (strict) + Zod

Строгая типизация всей кодовой базы. Zod валидирует каждый вход на сервере — расчёт на «вежливый клиент» запрещён.

🗄️

Supabase: Postgres + Auth + RLS

Аутентификация по email, изоляция данных на уровне строк (Row Level Security) — каждый пользователь видит только своё.

🎨

Tailwind CSS 4 + shadcn/ui

Фирменная тема «Midnight Violet»: тёмный конкурентный fintech-стиль, один фиолетовый акцент, контраст 7.2:1.

Архитектура

Модульный монолит: 9 фичевых срезов

src/ ├─ app/ # маршруты — только тонкая композиция ├─ features/ # срезы продукта: │ subscriptions analytics catalog │ upcoming-payments notifications │ billing payments auth overview │ ├─ components/ # UI │ ├─ actions/ # серверные действия + валидация │ ├─ data/ # ЕДИСТВЕННЫЙ доступ к Supabase │ └─ public.ts # фасад среза ├─ lib/ # деньги, даты, расписание биллинга └─ types/ # доменные модели
  • Однонаправленные зависимости: app → features → lib. Срезы не лезут во внутренности друг друга — только через фасад public.ts.
  • UI не знает про базу: компоненты получают готовые типизированные данные.
  • Общая бизнес-логика — в lib: деньги (целые минорные единицы!), расписание продлений, часовые пояса — одна реализация на всё приложение.
  • Выгоды: новый экран добавляется без риска сломать платёжный модуль; при росте можно вынести срез в отдельный сервис без переписывания.
Поток данных

Каждое изменение — через серверную проверку

Mutation (форма) │ ▼ Server Action ── Zod-схема ── повторная проверка прав (сессия, НЕ параметр) │ ▼ features/*/data ── типизированный клиент Supabase │ ▼ Postgres + RLS ── политика безопасности отрезает чужие строки даже если запрос составлен неверно

Сессия верифицируется

getClaims() проверяет подпись JWT — а не просто читает cookie.

Секреты — server-only

Service-role ключ зашит за серверный модуль и физически не попадает в браузерный бандл.

Проверено тестами

Отдельный набор тестов пытается читать чужие записи и доказывает, что нельзя.

Инженерные находки

Что было нетривиально

  • Деньги — только целые минорные единицы (копейки/центы): никаких дробей и ошибок округления в расчётах.
  • Общий движок биллинга, вынесенный в lib/billing-schedule — аналитика, календарь и напоминания считают по одному алгоритму, а не тремя разными.
  • Напоминания вне запросов: страницы никогда не отправляют письма. Единственный вход — закрытый по bearer-токену эндпоинт /api/notifications/dispatch, который выполняет идемпотентный «тик»: восстановление после сбоев → планирование → отправка порциями.
  • Платёжный шлюз SubHub Pro вынесен в изолированную плоскость: webhook с проверкой подписи (журнал → идемпотентное применение) и сверка состояния по расписанию. Реализован, но «спит» до включения (BILLING_MODE=off) — честнее спящей фичи, чем фейковой.
  • Снимки при создании — подписка хранит имя сервиса, тариф и цену на момент добавления; правка каталога никогда не переписывает историю пользователя.

Итоги

Готовый продукт, а не прототип

  • Рабочее веб-приложение: регистрация, ввод подписок, аналитика, календарь, напоминания, каталог — на реальной базе данных.
  • Спроектированная архитектура: 9 изолированных модулей, четкие границы слоёв, общий библиотечный движок.
  • Культура качества: 31 файл тестов, четыре обязательные проверки, и правило «не выдавать выдуманные данные за настоящие».
  • Защищённые данные: RLS на уровне базы, сессии с подписью, секреты — только на сервере.
